# Technical Baseline

Updated: 2026-08-12

## Scope

This baseline was recorded before acquisition-readiness refactors. It reflects the repository state, architecture boundaries, and verification status as observed locally on 2026-08-12.

## Repository Shape

- Frontend delivery is generated by `work/build_yellow_dashboard.py`.
- The generated app is a multi-page single-shell dashboard published into `outputs/`.
- Local backend flow is implemented in `work/dashboard_backend.py`.
- Netlify deployment flow is implemented with:
  - `netlify/functions/auth.mjs`
  - `netlify/lib/auth-store.mjs`
  - `netlify/lib/source-store.mjs`
  - `netlify.toml`
- Static assets and default content live under `work/assets/` and `work/content/`.
- Verification scripts live under `scripts/`.

## Runtime Architecture

### Public Layer

- Public project page
- Public prizes page
- Public rules page
- Public privacy page
- Public campaign snapshot embedded in the generated HTML

### Protected Layer

- Manager login and password-setup flow
- Authenticated admin dataset fetch
- Authenticated API source configuration
- Authenticated source refresh flow
- Manager-only control tabs for analytics and campaign design

### Data Flow

1. CSV source is loaded by the Python build script.
2. The builder creates:
   - public browser-safe HTML
   - Netlify publishable `index.html`
   - protected admin dataset JSON for authenticated access
3. Local backend or Netlify Functions expose auth/session endpoints.
4. Authenticated managers fetch the protected dataset after login.

## Storage Surfaces

### Local

- Auth database: `work/data/dashboard-auth.sqlite3`
- Source connector config: `work/data/dashboard-source-config.json`
- Optional dev auth persistence for Netlify verification: `work/data/netlify-auth-dev.json`

### Netlify

- Auth/session persistence through Netlify Blobs
- Source connector persistence through Netlify Blobs
- Protected admin dataset staged at build time in `netlify/data/admin-dataset.json`

## Auth Model

- Allowlist-based manager onboarding
- First login requires password creation
- Session cookie auth
- Rate limiting present in Netlify auth flow
- Single manager role only at baseline

## Existing Risks Identified At Baseline

### Critical

- Real manager emails were hardcoded in tracked source before remediation.
- Local protected dataset file contained real donor PII on disk and required strict git exclusion verification.
- Historical commits contain real manager emails and require manual history remediation planning before external diligence.

### High

- Manager access fallback behavior was too permissive for an acquisition-grade repository.
- Campaign-specific naming, branding, and config remain coupled to the current deployment story.
- Protected admin dataset is file-based rather than service-isolated.

### Medium

- Password reset and manager lifecycle controls are incomplete.
- Role separation is not implemented.
- API source configuration is protected but not yet governed by tenant or project boundaries.
